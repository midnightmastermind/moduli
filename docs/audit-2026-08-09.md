## 1. THE HEADLINE — every new day column clones a 128-row feed

**poms grid's Day Page template contains the Emotions Wheel, and APPLY_TEMPLATE clones the whole
thing into every day column.**

```
poms grid   Day Page TEMPLATE   136 descendants · 128 UNSIGNED (the emotions)
            day column Aug 6    136 descendants · 128 of them feed copies
            each NEW day costs  +136 occurrences  +136 modules
grid today  2637 occurrences · 2633 modules
```

The template's `Emotions Wheel` section carries `feed { enabled: true, limit: 1000 }`, so feedSync
materialises 128 emotion copies as its children. Those children are then cloned by APPLY_TEMPLATE.

**The clone is worse than a duplicate, because it is a duplicate of DERIVED data:**

| | template's wheel | the day column's clone |
|---|---|---|
| `feed` config | **yes** | **no** — APPLY_TEMPLATE does not copy the key |
| children | 128 | 128 |
| children carrying `meta.feedSourceId` | 128 | **128** |

So each column gets a graph that **can never re-materialise or self-heal** (no feed), holding 128
frozen copies that **feedSync will never sweep** (it only scans under a feed owner) and that every
tracker deliberately ignores (`meta.feedSourceId IS_EMPTY`). They are inert, permanent, and
multiply once per day.

**This was predicted and written down.** The 2026-08-07 docket, on test grid 2:
> *"test grid 2's Day Page template carries the whole Emotions Wheel … Worth deciding whether a fed
> graph belongs inside a template subtree before that shape reaches poms grid."*

It has reached poms grid. test grid 2's template is now only 7 descendants — so **the live grid and
the seed have drifted, in the direction nobody checked.**

**Proposed fix (one place, general):** APPLY_TEMPLATE should not clone an occurrence carrying
`meta.feedSourceId`. It is derived data owned by feedSync — if the clone carries the feed, feedSync
re-materialises it; if it does not (as here), it should not exist. Same posture trackers already
take, and the same posture feedSync takes about only sweeping what it minted. Then a cleanup
migration for the 128 already on the Aug 6 column.

**Not done here:** whether each day SHOULD have its own wheel (i.e. whether APPLY_TEMPLATE should
instead clone the `feed` key) is a product decision, not an audit finding.

## 3. The three "pre-existing" test failures are a HARNESS artifact, not a broken feature

`liveOpsBehavioral` has carried 3 red Daily-Question tests for several sessions, described each time
as "pre-existing". Nobody checked whether the feature works. **It does:**

```
poms grid   13 question containers with the signature · 12 FILLED
            the 1 empty is the TEMPLATE's own — which MUST stay empty (0040's own rule:
            a question baked into the template is handed to every future day)
```

Every real day column from Jul 28 through Aug 6 carries a distinct question from the pool. The
harness has the inputs too (117 question occurrences, the Reflection Questions module, the op
carries both the signature and the `PICK_RANDOM_FROM_POOL` step) — it builds the column and its
question container, and simply does not fill it in the same pass.

**Why this matters beyond the three tests:** on 2026-08-09 (6) a fourth failure was caught *only*
because the count went 3 → 4. Carrying a permanent red baseline is how the next real regression
hides. Decide: fix the harness to reflect the two-pass reality, or mark them harness-limited — but
do not leave them as ambient noise.
