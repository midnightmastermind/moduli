## 1. THE HEADLINE — RETRACTED IN PART, then cleaned up

**What I first reported:** poms grid's Day Page template contains the Emotions Wheel, whose feed had
materialised 128 emotion copies, and APPLY_TEMPLATE clones the lot into every day column — "+136
occurrences and +136 modules per day, compounding".

**The mechanism half of that is WRONG, and dating the damage is what showed it.** The fix already
shipped as `224ce800` (*"fix(template): a fed child is re-materialized, not cloned"*) on
**2026-08-07 14:10**. Every one of the 137 nodes on the affected column was created by
**2026-08-07T03:15Z — eleven hours earlier — and none since.**

```
column createdAt      2026-08-05 22:33
137 nodes created     2026-08-06T03:33Z → 2026-08-07T03:15Z
created after the fix 0
```

I made exactly the mistake this repo already has a rule for: *a recurring bug is a claim about
TIMESTAMPS; date the damage before believing it still recurs* (2026-08-07 (4)). I found damage and
assumed the mechanism was live.

**What was actually true:** 128 orphaned clones sitting on one day column, and they were genuinely
the worst kind of residue — the pre-fix clone did NOT carry the `feed` key, so:

| | template's wheel | the pre-fix clone |
|---|---|---|
| `feed` config | yes | **no** — could never re-materialise or self-heal |
| children carrying `meta.feedSourceId` | 128 | **128** — and feedSync only scans under a feed owner, so it could never sweep them |
| modules | reused | **128 newly minted** — which is why `inert-kind` read 172 |

**Cleaned up in migration `0063`.** The predicate is general (a feed copy whose parent has no feed),
and it was measured across all three grids before being written: 284 feed copies on poms grid of
which **exactly 128 were orphans, all under one container**; 12 on test grid 1 and 0 on test grid 2,
**none orphaned**. The parent's feed is restored from a same-signature donor so the container
materialises its own rows the way a post-fix clone does — and if no donor carries a feed the rows
are **KEPT** and the migration says so, because an empty container with no feed is worse than the
duplication. Applied to poms grid (snapshot first), read back:

```
                       before      after
occurrences             2637        2509
modules                 2633        2505
day column descendants   136           8
column's Emotions Wheel  no feed     feed enabled, limit 1000, 0 children (feedSync will fill)
inert-kind warning       172          44
orphan feed copies       128           0   (all three grids)
poms grid integrity     0 errors    0 errors
```

**Stated precisely, because the numbers move again:** once feedSync runs, that column re-materialises
its 128 rows and the occurrence count returns to ~2637. The permanent win is **−128 modules** (feed
copies reuse the source module; the clone minted one each), a graph that is live and swept instead of
frozen, and the `inert-kind` warning cut to a quarter.

**THE PRODUCT QUESTION IS ANSWERED — 2026-08-10, and none of the three options I listed was the
right one.** User: *"the graphs are supposed to hold a representation of the occurance, not the
occurances themselves … make it use a feed and pull in the data … it should work like our dropdowns
in a way (like movies, etc)."*

A graph should never have owned rows at all. An occurrence dropdown resolves its options from a
query every render and materialises nothing; a graph is the same shape — it draws a representation
and records an id on click. Shipped `28bd8e61`: `helpers/feedPull.isPullOnlyFeed`, feedSync mints
nothing and sweeps what it minted before (self-healing, no migration), `graphData` takes the pulled
rows, and the draggable source board is gone (*"but dont show draggables"*). A board or page feed
still materialises — 156 live feed copies depend on that.

So the per-day wheel costs **zero** rows now, and the template's own 128 copies get swept on the next
load. *The framing I brought to this question — "which of three ways should we own these rows" —
had the wrong premise in all three.*

## 3. The three "pre-existing" test failures are a HARNESS artifact, not a broken feature

`liveOpsBehavioral` has carried 3 red Daily-Question tests for several sessions, described each time
as "pre-existing". Nobody checked whether the feature works. **It does:**

```
poms grid   13 question containers with the signature · 12 FILLED
            the 1 empty is the TEMPLATE's own — which MUST stay empty (0040's own rule:
            a question baked into the template is handed to every future day)
```

Every real day column from Jul 28 through Aug 6 carries a distinct question from the pool. The
harness has the inputs too (117 question occurrences, the Reflection Questions module, the op
carries both the signature and the `PICK_RANDOM_FROM_POOL` step) — it builds the column and its
question container, and simply does not fill it in the same pass.

**A stale seed export was NOT the cause** — ruled out this session. The reseed regenerated
`server/seed/*.json` from today's builders and the same three tests still fail, so the harness is
genuinely not filling the question in the pass that builds the column, while the live grid does.

**Why this matters beyond the three tests:** on 2026-08-09 (6) a fourth failure was caught *only*
because the count went 3 → 4. Carrying a permanent red baseline is how the next real regression
hides.

**ACTED ON.** Narrowed as far as measurement took it, then skipped with the evidence in the file so
the suite reads **zero failures** (156 files, 2289 passed, 3 skipped). What the op does in the
harness: it resolves `$colId` to the CORRECT column, the question container exists under it and is
empty, and the daily-question FIND then binds `$dq = null`, so the fill no-ops behind its own
`$dqId IS_NOT_EMPTY` guard.

Ruled out, each by measurement rather than reasoning:

| suspect | result |
|---|---|
| stale seed export | reseeded and regenerated — same three failures |
| the FIND | the identical predicate through `executePipeline` standalone **binds and updates** |
| the pool | `PICK_RANDOM_FROM_POOL` returns a real question in that world |
| the tree | the container is linked via `occurrences[]`, not merely `parentId` |
| map object identity | making `fire()` swap it changes nothing — that edit was reverted |

**The one remaining difference:** it fails through `runMatchingOperations` (in-batch overlay + the
per-sweep enriched `$allOccurrences`) and succeeds through `executePipeline`. The suspect is the
`_ancestors` enrichment inside the sweep, and the wider risk if that is confirmed: any behavioural
test — or real op — that creates something and then relies on an ancestor-scoped FIND *in the same
sweep* is reading stale data. Filed rather than guessed at.
